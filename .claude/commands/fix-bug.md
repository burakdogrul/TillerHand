description: Finds the bug's root cause, writes a regression test, then fixes it.
argument-hint: [bug description, error message or steps]
---

Bug: $ARGUMENTS

Load the `mattpocock-skills:diagnosing-bugs` skill and apply its loop. Use `ponytail:ponytail` while fixing (smallest complete fix). Patching the symptom is forbidden. In order:

1. **Reproduce.** Find the shortest steps that trigger the bug. If you cannot reproduce it, stop and ask me for more information (log, screenshot, steps).
2. **Gather evidence.** Read the relevant code, the logs and the recent changes (`git log -p -- [dosya]`). When did the bug start?
3. **Form hypotheses.** The 1-3 most likely root causes. For each, a check that would confirm or refute it. Change one variable at a time; also write down the evidence that refutes a hypothesis.
4. **Verify.** Run the checks. Do not move to the fix before the root cause is proven. If the root cause is in a single feature folder, suggest `/freeze <klasör>` so the fix does not spread.
5. **Red test.** The one who will make the fix does not write the test that shows the bug (AGENTS.md rule 7): run the `test-writer` subagent with the test role's model. The prompt contains the reproduction steps, the expected behavior and the public interface of the relevant code, and no root-cause hypothesis and no fix idea. The agent writes the test and shows that it fails. Only `test-writer` can write to test files. Write a short bug spec: `docs/product/specs/<hata-kısa-adı>.md` (`_template.md`, Tür: hata), a few lines are enough. In the `**Sınıf:**` line write exactly one of this list: `boş-girdi`, `doğrulama`, `yetki`, `tarih-saat`, `yerel-dil`, `sıralama`, `eşzamanlılık`, `yapılandırma`, `dış-servis`, `sözleşme`, `arayüz-durumu`, `diğer`. The current behavior is the reproduction steps, the expected behavior is what the test checks. Under the must-not-change behavior, write the acceptance criteria near the bug that have tests, with their ids (`- Ö-01.1: ...`); if there are none, leave the section empty.
6. **Fix.** If there is more than one way to fix (e.g. a quick patch versus a lasting fix or a behavior change), **ask as a decision** which one to choose. Fix the root cause once, in the shared code. Check whether other callers have the same bug.
7. **Green.** The new test and the existing tests pass: run the command in this turn and show its output. Then run the gate: `node .claude/hooks/gate.mjs --run` (lint, type check, test, Semgrep; the commit meeting uses this output). Fix anything red. If it says "Komut onayı gerekli", show me the commands; if I approve, run `node .claude/hooks/gate.mjs --approve`. If you set a lock, run `/freeze off`.
8. **A repeat?** If another bug spec under `docs/product/specs/` has the same `**Sınıf:**` value (and the class is not `diğer`), this bug class is repeating: propose a single rule that prevents the repeat. If it can be checked mechanically ("do not write Y in file X", "W is required in call Z"), it becomes a `/hookify` rule (`.claude/hookify.<ad>.local.md`; do not add it to `.gitignore`, it goes into git and the team uses it too). If it cannot be checked mechanically, or hookify is off (Light profile), or you are outside Claude Code, add one line to `AGENTS.md` → "Öğrenilen kurallar" (learned rules; if the section does not exist, open it at the end of the file). Source and date line: `(kaynak: specs/<a>.md, specs/<b>.md · YYYY-AA-GG)`; at the end of the rule in AGENTS.md, in the last line of the message body in the hookify file. Ask with AskUserQuestion, showing the rule text and the target file: Add / Later (reminded on the dashboard) / Not needed. If there is no approval, write to no rule file. Write the Add or Not needed answer to the specs of the same class with a `**Kural:** <hedef dosya veya "gerek yok"> · YYYY-AA-GG` line; the dashboard warning closes and the decision is not asked again.
9. **Report:** Root cause (1 sentence), the fix, the added test, similar risky places, the added rule (if any).

If you cannot solve it in 2 attempts: stop, write what you tried and what you ruled out, ask for direction.
Last resort: find the commit that introduced the bug with `git log` (`git bisect`), and proceed from there.
