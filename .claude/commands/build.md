Task: $ARGUMENTS
If empty, take `docs/workflow/progress.md` → "Next step" (next step), or the first unchecked task in `docs/product/roadmap.md`.

0. **Limit and context:** Read the limit and record the start: `node .claude/hooks/progress.mjs --start` (the desktop has no status line: pass `--limit <5-hour %>`, taken from `get_usage`). If context is past 50%, first suggest `/wrap-up` + `/clear`. If the level is yellow/red or the estimate exceeds the remaining share, say so in one line and start (`docs/workflow/usage-limits.md` §3; do not ask). If `docs/workflow/progress.md` → "Where we left off" (where we left off) is filled, continue from there.
0b. **Model and effort** (`docs/workflow/models.md`): Read the last choice with `node .claude/hooks/models.mjs --show`. There are five roles, one question per role (model and effort together, e.g. "Sonnet · high"; options are in models.md). Make two AskUserQuestion calls: first plan, code, test; then review, docs. In each question put the recommended option from models.md first, labeled "(Recommended)". If the last choice differs, write "last choice" in that option's description. In the test question, the recommended model differs from the code role's last choice (models.md). Save the answer with `node .claude/hooks/models.mjs --set plan=<model>:<effort> code=… test=… review=… docs=…`. If code and test use the same model, the script warns: pass the warning to the user. If the main session's model or effort differs from the plan role, suggest `/model <name>` and `/effort <level>` in one line. If the `cost` topic is closed in question mode, do not ask and do not run `--set`: the last choice stays valid; write "automatic" in the status block.
1. Restate the task and its acceptance criteria to me in one sentence. Update the active task in `docs/workflow/progress.md`.
2. If there is no approved plan for this task and it touches more than 2 files, first apply the `/plan-task` steps (including decision points), then wait for approval.
2a. **Flow:** `node .claude/hooks/flow.mjs --files <number of files in the plan>` (the desktop has no status line: pass `--context` and `--limit` from `get_usage`). The output says where code and docs work run (main session / subagent), and how many members the end-of-task board uses and whether they meet in parallel or in sequence (re-run it at 6b: it suggests members by name from the changed paths). Steps 2c, 6b and 8 follow it. If it says "Suggest /clear first", suggest it in one line.
2b. **Tests first, with a separate agent:** The code writer does not write the tests (AGENTS.md rule 7). Whatever the flow says, run the `test-writer` subagent with the test role's `model` and `effort`. Give the prompt only: the task, the acceptance criteria, the spec if any, and the public interface of the code to be touched (signatures, API paths). Do not give the approved plan's implementation details or ready-made test code: a test checks the requested behavior, not the plan. The agent writes the acceptance tests (criterion id in the test name: `AC-01.1`) and, if needed, adversarial tests, runs them and shows that they are **red**; show me the red output. If it reports an unclear criterion, ask me the question yourself. Only `test-writer` can write to test files: if the main session or the code agent tries, the test guard blocks it.
2c. **Hand off to the code role (2c and 3):** If the flow says "Kod: ana oturum" (code: main session; a small task: the subagent's cold start costs more than it saves), write the code yourself per step 3. Otherwise run a subagent with the Agent tool and pass the code role's `model` and `effort` in the call. Prompt: the task and acceptance criteria, the approved plan, the files to touch, the rules in step 3, and the red tests from 2b (goal: turn them green; it does not touch test files). A subagent cannot ask the user: at a decision point it must stop and report the question and options; you ask the question, write the decision to the log, and continue the subagent with the answer. Resume the same subagent with SendMessage for fixes or continuation too; do not start a new agent (it would re-read the files). Ask for a short report (at most ~15 lines: changed files, test result as numbers, open questions; no code and no full output). When the subagent finishes, read the diff and the test output yourself; step 4 onward runs in the main session. Put the user-visible text (humanizer) into its final form yourself.
   **If a test looks wrong:** The code side does not change the test. It reports the reason; resume `test-writer` with SendMessage and let it decide per the criterion. If the criterion changes, that is a decision: ask the user.
3. Implement. Rules:
   - **If a new decision point appears while implementing, stop and ask** (`docs/workflow/decision-protocol.md`). Do not guess and continue.
   - Skills (`docs/workflow/skills.md`): `ponytail:ponytail` for code, `mattpocock-skills:tdd` for critical flows. For UI, the chosen direction skill + `impeccable:impeccable` (stay bound to `DESIGN.md`; if a new design decision is needed, `/design`). `humanizer:humanizer` for user-visible text.
   - Only this task's scope. Do not fix problems outside the task; write them to `docs/workflow/progress.md` → "Open issues / blockers".
   - If the code map is connected, explore with it; do not read files wholesale. In a large file, search first (grep), then read only the needed line range.
   - If the package gate warns while installing a package (made-up / too new / rarely used), tell the user; do not try to force it.
   - If the plan needs a feature flag, put the feature behind a flag and add it to `docs/operations/feature-flags.md`.
   - If the limit reaches 90% / 95% / 99% while working, give the warnings in `docs/workflow/usage-limits.md` §4; do not stop the work.
   - Use the existing patterns in the project.
   - Do not forget error, empty and loading states.
   - If you touch a critical flow (`docs/quality/test-plan.md`), add a test.
   - New environment variable → `.env.example`.
   - New package → the lock file goes into the commit. New system dependency (database, ffmpeg, etc.) or setup step → `README.md` → Requirements / Installation.
4. Verify: `node .claude/hooks/gate.mjs --run` (lint, type check, test, Semgrep; the end-of-task and commit meetings use this output). Fix anything red. If it says "command approval needed", show me the commands; if I approve, run `node .claude/hooks/gate.mjs --approve`. If you cannot fix the same error in 2 attempts, stop and explain the state to me.
5. **Produce evidence.** "It should work" is not enough; show that it works. The method is in `docs/architecture/stack.md` → "Verification":
   - UI change → `node .claude/hooks/preview.mjs <task id>`: it opens the dev server, writes desktop (1440) and mobile (390) screenshots to `.previews/<task id>/`, and closes the server. The first run can take a few minutes because of the Playwright download and the first build: give the command a 10-minute timeout. Open the images and show them to me. If the script says "command approval needed", show me the commands; if I approve, run `node .claude/hooks/gate.mjs --approve`. If it gives another error, write the message in the report and take the screenshot by hand. Then try the main scenario and one error scenario on the relevant screen. To prove the task's UI acceptance criteria in the browser, suggest `/qa` in the report.
   - API/business logic → send a real request or run the test; show the request and the response.
   - If you cannot produce evidence (device, panel, payment, etc.), say so clearly and write the steps I must do.
6. If the UI changed, run `impeccable:impeccable` → `critique`; ask me whether to fix the important findings.
6b. **End-of-task board meeting** (`.claude/board/rules.md`; if the board is set up). This is the only full review of the change: the board members relevant to the change, in the number the flow (2a) says (at most 3), + `code-reviewer` (+ `security-auditor` if the change touches a sensitive path such as auth, payment or personal data), with the review role's `model` and `effort`. If there is a REJECT, the task is not done; ask with the finding and the options. If the verdict is APPROVE or CONDITIONAL and the gate (step 4) is green, run `node .claude/hooks/commit-gate.mjs --approve "task end: <attendees>"`: the commit does not convene the board again for the same changes; if files changed afterward, only those are reviewed. Write the meeting to the `docs/workflow/board.md` log. If the board is not set up, suggest `/review-changes` in step 9.
7. Check the "done" list in `AGENTS.md` → "Definition of "done"" one by one.
8. Close the scope shield (the command asks the user): `node .claude/hooks/freeze-guard.mjs --plan-end`. In the PRD, check off only the criteria whose tests are green. Run the tests with a JUnit report (`docs/architecture/stack.md` → Acceptance tests and feature flags) so the dashboard updates. Read the limit again. Writing the roadmap, the cost log and progress is mechanical: do not spend model calls; write it with one command:
   `node .claude/hooks/progress.mjs --done <task id> --cost "<task id> <short name>" <S|M|L> --task "-" --did "<task id>: <one line on what was done>" --next "<next task>" --check`
   `--cost` takes the start from step 0 and computes the end and the duration itself (on the desktop add `--limit <%>`). `--check` validates the bold-labeled lines of progress.md (the status line and the dashboard read them); fix them if broken. Write plain-text sections such as open issues and pending decisions by hand if needed.
9. Give the report:
   - What was done (2-3 lines)
   - Decisions made in this task (user / automatic)
   - Evidence (screenshot, request/response, test output)
   - How I should test it (step by step)
   - Suggested commit message
   - Places you could not check or are unsure about
   - If I corrected your behavior or stated a preference during the task: in the same AskUserQuestion call, a separate multi-select question "Save as a preference?" (AGENTS.md → rule 9, if present; save the selected ones with `prefs.mjs --add`). If there are no notes, do not ask.
   - Ask "What next?" with AskUserQuestion: commit (Recommended; the end-of-task review is valid; if the board is not set up, `/review-changes` first) / move to the next task / ask for changes in this task. At commit, a light board review is requested automatically (commit gate hook). After the commit is made and the tests are green, save a working point: `node .claude/hooks/checkpoint.mjs --save "<task id> done, tests green"` (`/rollback` returns here).
   - If the commit was made: check that `docs/workflow/progress.md` → "Next step" (next step) is current, then suggest `/clear` in one line (task = session, `docs/workflow/usage-limits.md` §3; independent of the context percentage). The new session continues from progress.md.
