## Commentary

- **Still no difference in correctness.** On the hard tasks too, both conditions passed all hidden tests. Sonnet solves tasks of this size correctly without the kit as well.
- **The difference is in test quality.** The tests the kit wrote caught twice as many of the planted bugs. The biggest gap is in the implicit-requirement and trap tasks: trash 6/12 against 0/12, tr-sort 4/6 against 0/6, paging 6/6 against 3/6. The run without the kit writes the code correctly but mostly does not leave the test that would protect that behavior at the next change.
- **The gap in bug-sort is larger than measured.** The agent without the kit wrote no regression test in any of the 6 runs. The kit agent's tests are stricter than the request: sorting that accounts for time zones, and 400 for an invalid date. The reference solution does not do these, so these tests dropped out of the mutant measurement. The measurement counts tests against the reference's interface.
- **The kit followed the process.** In all 24 runs it wrote the test before the code. It ran the gate (`gate.mjs --run`) in 18 runs; in the 6 bug-sort runs in the `/fix-bug` flow the gate never ran. This is a gap in the kit.
- **The price is 2× cost and 1.8× time.** Part of this is fixed load: rules, hooks and command text enter every session. Tokens are 2.9×, but most of them are read from the cache.

## Limits

- n = 3-6. The ranges are narrow. There is no spread in hidden tests; within a task the spread in mutants is at most 1.
- In the kit condition, the plugins enabled in the kit's `settings.json` were loaded (caveman, impeccable, humanizer, ponytail, mattpocock-skills). They were not loaded in the condition without the kit.
- Some of the runs were done at the same time: for bug-sort and trash, two sets of runs overlapped. The times may be slightly affected by this.
- There is no user in a headless run. The kit's value in asking questions and in the board is not measured.
