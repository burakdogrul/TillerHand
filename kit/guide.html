Why

Writing code with AI is fast. Shipping a product is a different job.

With "vibe coding" a demo takes an afternoon. A product that real users touch can't survive silent decisions, untested code, leaked keys and a messy folder tree. TillerHand keeps the speed and closes these four gaps.

UsuallyThe AI picks the database, the library and the data model on its own. Nobody knows why.
With TillerHandEvery decision comes to you with 2-4 options: the recommended one first, with when each is better and what it costs. Your answer goes into the log and is never asked again.
Usually"It works" is the only proof, and there are no tests. The next change breaks the last one.
With TillerHandAcceptance tests are written before the code and start red. Before "done", proof is shown: test output, a screenshot.
UsuallyAn API key lands in the code, the prod database gets deleted by accident, a test is weakened so it passes.
With TillerHandHooks stop these before they happen. The AI can't bypass these guardrails; every step toward prod needs your approval.
UsuallyThree months later nobody knows where the files are; final-v2-old.tsx multiplies.
With TillerHandA feature-based folder map is enforced when files are written, in CI and in review. Clutter files are blocked.

How it works

The same cycle for every task. You sit in the middle.

TillerHand is a way of working, not a list of commands. You write your idea and walk through the rest with the AI, step by step. Nothing important happens without you knowing.

  1. 1

    The AI plans

    Reads the task, finds the decision points, prepares the options.

  2. 2

    You decide

    Recommended option first; when each is better, and what it costs.

  3. 3

    Test first, then code

    A separate agent writes the tests and they start red; the code turns them green.

  4. 4

    The board reviews

    The relevant experts review; a critical finding means the task is not done.

  5. 5

    Saved with proof

    If the gate is green: commit, dashboard update, next task.

Without coding

If you're new: step by step

You don't need to know how to code. Claude does the git, terminal and install work and asks you at every important step. You describe what you want and make the choices.

  1. Accounts (once): a GitHub account (free) and a Claude Pro or Max subscription.
  2. Programs (once): the Claude desktop app, Node.js (LTS version), Git. You can also install GitHub Desktop if you like.
  3. Project: Create a folder for your project and select it in the Code tab of the Claude desktop app. Tell Claude "run npx tillerhand init in this folder". If you've installed the TillerHand plugin once, /tillerhand:init works too.
  4. Open: Open a new session in the same folder; the kit's commands and guardrails load in the new session. If it offers to install the plugins, accept.
  5. Start: Type /start your idea (or /adopt if you already have code). The first option of every question is the recommended one; if you're unsure, pick it. If you're on Pro, suggested answers for the first questions: profile Light, planning depth Quick (~25-35% of your 5-hour limit), dashboard Yes, narrator mode Yes.
Good to know. Pro has a 5-hour and a weekly usage limit; Claude warns at 90%, 95% and 99% but does not stop the work. If the limit runs out and the work is cut off, you continue from where you left off with /build after it resets. Decisions such as database, design and cost are never made without asking; hard-to-undo steps such as payment, data deletion and going live always need approval. To hand the project to someone else use /handoff; the new owner continues from the same place with /handoff take.

Council: three stages

Karpathy's llm-council structure, adapted to the board. Heavy meetings and decisions that are expensive to reverse go through three stages:

1 · First opinions

Members (or advisors on different models) work in parallel without knowing about each other. Opinions are labeled A, B, C; findings A1, A2…

2 · Anonymous cross-vote

Each member reads the others' opinions without knowing who wrote them, votes each finding AGREE · OVERSTATED · DISAGREE, writes what is missing, and ranks the opinions.

Count (code)

council.mjs computes the average rank, the finding votes and the consensus percentage in code; the model can't change the numbers.

3 · Chair

board-chair (opus) reads the minutes, writes the decision, drops refuted findings with a reason, and keeps the minority opinion. It can't drop a disputed critical finding; it asks you.

The profile decides when the council meets (one council costs about 12% of the 5-hour limit on Pro):

The "(Recommended)" option of a question asked in the decision council comes from the council; under each option you see the council's vote and the minority opinion. Minutes are in docs/workflow/council/, with a summary in the dashboard's Board tab.

When a REJECT comes, the task is not counted as done. You get three options: fix it (recommended), accept the risk and record the reason, or roll the task back. If members disagree, the two opinions are shown side by side and the decision is asked from you.

Rules are written, checks are automatic

Guardrail layers

Decisions are made in Claude Code's permission layer (allow · ask · block); the AI can't bypass them. In Codex and Antigravity the same scripts run through that tool's hooks.

LayerWhat it does
Secret blockBlocks API keys (Anthropic, OpenAI, Stripe, AWS, GitHub, Supabase…) written to code or docs; also scans before a commit
Destructive command shieldDROP, TRUNCATE, unconditional DELETE, db reset pulling prod environment variables onto the machine and deleting cloud data (S3 buckets, databases, resource groups, apps, repositories) are blocked; prod deploy, rollback, store submission, migrations, cluster and hosting deletes, package and release publishing and deleting the main branch are asked
Package gateA package that is installed, or downloaded and run with npx or uvx, is checked against the registry: if it doesn't exist it is blocked; if it is very new, rarely downloaded or looks like a popular package, it is asked. A git or URL source, another registry or index, and cargo, go, gem and composer installs are asked, since they cannot be checked. Dependencies the AI adds to package.json, requirements.txt or pyproject.toml go through the same check
Structure guardA new file outside the map is asked; clutter such as *.bak, *-old.*, copies and temp/ is blocked; made from the shell (cp a.ts a.bak) it is asked
Config approvalCLAUDE.md, AGENTS.md, .claude/, .codex/, .mcp.json and workflow files don't change without your approval
Test separationThe tests are written before the code by a separate agent (test-writer, a different model is recommended), not by whoever writes the code. Nobody but this agent can write to a test file: the main session and the code agent are blocked if they try. A test file changed indirectly by a patch or script also stops at the commit gate. So whoever writes the code can't shape the test to fit their own code
Test protectionDeleting or commenting out an assertion, .skip/.only, a loosened assertion, deleting or moving a test file, and narrowing coverage in the test config are asked; so is writing to a test file through the shell
Deterministic gategate.mjs --run: lint, type check, tests and Semgrep run; the output feeds the board, and a red check counts as REJECT. If the "must not change" behaviors in the spec have no test or the test is red, the gate is red. It is also red if an added line contains a path specific to this machine (the full path of the project folder or the home folder). A new or changed command is first shown to you for approval
Commit gateNo commit without a board review and a green gate for the same changes; the task-end approval also counts for the commit, so the same change is not reviewed twice; skipping the review (--skip) is asked every time
Edit lockWhile /freeze <folder> is on, the AI writes only to that folder; writing outside through the shell is asked, and a symlink can't escape it
Scope shieldAfter /plan-task approval, the plan's file list is saved; writing to an existing file not on the list is asked. Turning the shield on and off is asked too

/findings-* · docs/findings/

Findings reports

Scans the project through an expert's eyes and ranks the most important findings, at most 20, with evidence, a 0-100 severity score and a technical fix. Each report gives a health score for its area and is compared with the previous one (new / continuing / worse / resolved).

CommandPoint of viewExample finding
/findings-techSenior architectThe same authorization check is rewritten in 4 places; an unused export; an N+1 query
/findings-businessThe industry's senior expert (a banker in banking); with web researchNo reconciliation flow; the refund rule is undefined; a feature that competitors have as standard is missing
/findings-securityAttackerSomeone else's invoice can be read (IDOR); the webhook signature is not verified
/findings-uxUser and UX researcherThe empty list screen gives no direction; contrast is 3.1:1

/findings-legalCompliance expert (not legal advice)The tax number is missing from the data inventory; the cookie banner loads analytics before consent

Severity score = impact (40) + likelihood (25) + spread (20) + urgency (15). Levels: Critical ≥80 · High 60-79 · Medium 40-59 · Low <40. Health = 100 − penalty (critical 15 · high 8 · medium 4 · low 1). At the end of the report are the fix plan, the relevant board member's opinion, and the question of which findings go into the roadmap.

The code is organized by feature: everything that belongs to a feature lives under features/<feature>/. If a new file is about to be written outside the structure map, you are asked; clutter files are blocked. Trial work goes to sandbox/, outdated docs to docs/archive/.

AGENTS.md · CLAUDE.md · README.md · CHANGELOG.md
AGENTS.md holds the shared rules (read by Claude Code, Codex and Antigravity); CLAUDE.md imports it and carries the Claude Code-specific additions. The structure is protected in four places: the hook at write time, CI on every PR, the board's Architect, and /findings-tech. Changing the map is a technical decision; you are asked and it is recorded as an ADR.

docs/workflow/usage-limits.md

Limit awareness

Before work starts, the 5-hour and weekly limits are read: on the desktop with the get_usage tool, in the terminal and IDE from what Claude Code sends to the status line. The limit is only a reason to warn: work doesn't stop, and continues until you say "stop".

While workingWhat happens
90%A one-line reminder and the reset time; work continues
95%A "limit is almost gone" warning; where it left off is saved quietly
99%A "work may be left unfinished" warning; steps are kept small, a WIP commit is suggested
If you say "stop"Stops safely: finishes the step, runs the tests, writes where it left off
Level5-hourWeeklyBehavior
green< 60%< 70%Works normally
yellow60–84%70–89%States the estimated cost, the board is halved
red≥ 85%≥ 90%States the cost and the remaining share in one line
Task costs are written to docs/workflow/cost-log.md; estimates settle on real data over time. At session start only the summary rules and docs/workflow/progress.md are loaded (about 1,700 tokens). If the code map is connected, the code is queried without reading the files. The main session's context is kept small too: independent questions are asked in one round, gate and subagent reports come back short, and /clear is suggested once a task is done and committed.

Rules that learn

Personal preferences

~/.vibe-kit/preferences.md · prefs.mjs

  • When you correct a behavior or say how you want to work, the AI takes a note
  • At the end of a task and a session it asks "save this as a preference?"; what you don't approve is not written
  • Preferences apply to all your projects and load in every session; they don't go into git
  • List: node .claude/hooks/prefs.mjs --list, remove: --remove <no>

Model per role

docs/workflow/models.md · models.mjs

  • Five roles: planning, coding, test writing, review, docs and research
  • One question per role at the start of each task (model and effort together), on two screens
  • Recommended: plan Opus, code Sonnet, tests Opus, review Sonnet, docs Haiku; all at high effort. Tests use a different model from the code: they don't share the same blind spot
  • Test, review and docs work runs in a subagent with the chosen model; the plan runs in the main session
  • The roadmap mark, the cost line and the progress labels are written by progress.mjs; no model call is spent and the format doesn't break
  • A subagent only when it pays off: flow.mjs looks at task size, context and limit; a small task stays in the main session, board members are chosen from the changed paths and their number shrinks with the limit; a member writes at most 5 findings

In every project

Golden rules

  1. You make the decisions.The AI recommends and gives reasons; the choice is yours. On a topic where you haven't said "don't ask", it doesn't choose on its own.
  2. Choose design by seeing it.You pick the screen in the preview, not a style described in words.
  3. Write first, then have it coded.No code without a PRD and an out-of-scope list.
  4. One task, one session.Split a big task.
  5. Every working step is a commit.If the AI loses its way, you go back to there.
  6. Go live on day one.Have the deploy pipeline and CI working from the start.
  7. Context lives in files.Make /wrap-up and /clear a habit.
  8. Proof, not "it works".A screenshot, a request/response, test output.
  9. The two-attempt rule.If the same error isn't solved in two attempts, stop, go back, and re-plan.
  10. Secrets never go to the client.Everything that goes to the browser and the mobile bundle is public.
  11. A backup you haven't tested isn't a backup.Try the restore before launch.
  12. Turn a repeated error into a rule.Write it to the kit with /retro; if you can, turn it into a hook or a CI step.
